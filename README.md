# inHabit

inHabit — веб-приложение для отслеживания привычек в командах, которые называются гильдиями. Владелец гильдии задаёт привычки, расписание и награду. Участники отмечают выполнение, получают очки опыта (XP) и сравнивают результаты в лидерборде. На главной отображаются привычки на сегодня с учётом часового пояса пользователя, а в профиле — суммарный XP, уровень и серия активных дней.

## Технологический стек

| Компонент | Технологии и назначение |
| --- | --- |
| Frontend | React 19 и React Router 7 для интерфейса и навигации, Vite 7 для разработки и сборки, pnpm для зависимостей |
| Backend | Python 3.12, Django и Django REST Framework для API, Simple JWT для аутентификации |
| База данных | PostgreSQL 16 для пользователей, гильдий, привычек и отметок выполнения |
| Локальный запуск | Docker Compose запускает базу, backend и frontend. Nginx раздаёт собранный frontend и направляет запросы `/api/` на backend |

## Локальный запуск

Понадобится запущенный Docker с Docker Compose. Выполните команды из корня репозитория, где лежит `docker-compose.yml`.

При первом запуске скопируйте `.env.example` в `.env`:

```powershell
Copy-Item .env.example .env
```

В Linux или macOS используйте `cp .env.example .env`.

Запустите сервисы и примените миграции:

```bash
docker compose up --build -d
docker compose exec backend python manage.py migrate
```

Откройте [http://localhost:5173](http://localhost:5173). Если в `.env` задан `FRONTEND_PORT`, используйте указанный там порт. Backend доступен на `http://localhost:8000`, API — по префиксу `/api/`. Для остановки выполните `docker compose down`.

### Режим разработки frontend

Для разработки с автообновлением понадобятся Node.js 24 и pnpm 11.19.0. Запустите в Docker только базу и backend, чтобы освободить порт 5173 для Vite. Примените миграции, если база ещё пустая.

```bash
docker compose stop frontend
docker compose up --build -d backend db
docker compose exec backend python manage.py migrate
cd frontend
pnpm install --frozen-lockfile
```

Задайте адрес backend для Vite и запустите frontend.

```powershell
$env:VITE_PROXY_TARGET = 'http://localhost:8000'
pnpm dev
```

В Linux или macOS выполните `VITE_PROXY_TARGET=http://localhost:8000 pnpm dev`. Откройте [http://localhost:5173](http://localhost:5173).

| [Главная](http://localhost:5173/) | Посмотреть привычки на сегодня и открыть одну из своих гильдий |

## Спринт 1: текущее состояние

Реализованы подготовка и истории 1–6:

- Создание гильдии с владельцем и просмотр только своих гильдий.
- Создание привычки владельцем: название, ежедневное расписание или выбранные дни недели.
- Сложность и вес награды: лёгкая — 10 XP, средняя — 20 XP, сложная — 30 XP; награда = базовые XP × вес (1–10).
- Форма добавления привычки и список привычек на странице гильдии. Демо доступно по `/guilds/demo`, данные демо сохраняются в текущей сессии браузера.
- Регистрация, вход и выход по JWT. Защищённые страницы перенаправляют гостя на вход; запросы к API выполняются только с `Bearer` access-токеном.

- Участник может отметить привычку выполненной и получает её XP. Повторная отметка той же привычки в тот же день не меняет XP: это обеспечено уникальным ограничением базы данных.
- Список «Сегодня» учитывает часовой пояс пользователя и расписание привычек.

### Регистрация и вход

Откройте `/register`, чтобы создать учётную запись, либо `/login`, чтобы войти. После успешного действия приложение сохраняет access- и refresh-токены в `localStorage`; вручную добавлять токен через DevTools больше не нужно. Access-токен действует 15 минут, refresh-токен — 7 дней. При выходе refresh-токен отзывается сервером, а данные сессии удаляются из браузера.

API аутентификации:

- `POST /api/auth/register/` — `{ "username", "email", "password", "timezone" }`;
- `POST /api/auth/login/` — `{ "username", "password" }`;
- `POST /api/auth/refresh/` — обновление access-токена;
- `GET /api/auth/me/` — текущий пользователь;
- `POST /api/auth/logout/` — `{ "refresh" }`, отзыв refresh-токена.

### API привычек

Все запросы требуют заголовок `Authorization: Bearer <access_token>`.

- `GET /api/habit-difficulties/` — справочник сложности и базовых XP.
- `GET /api/guilds/<guild_id>/habits/` — список для участников гильдии.
- `POST /api/guilds/<guild_id>/habits/` — создание только владельцем.
- `POST /api/habits/<habit_id>/complete/` — отметить выполнение привычки участником гильдии.

- `GET /api/habits/today/` — привычки на текущий день в часовом поясе пользователя (`users.User.timezone`). Ответ содержит локальные `date`, `timezone` и привычки с названием и цветом гильдии.

Пример тела создания:

```json
{
  "name": "Утренняя зарядка",
  "schedule": "weekdays",
  "weekdays": [1, 3, 5],
  "difficulty": "medium",
  "xp_weight": 2
}
```

Дни недели используют ISO-нумерацию: понедельник — 1, воскресенье — 7. Для `daily` список дней нормализуется в `[]`. Поле `xp_reward` рассчитывает сервер (в примере — 40 XP); клиент не задаёт награду напрямую. Название ограничено 120 символами. Ответ гильдии содержит `is_owner` для отображения доступных действий.

### Отметка выполнения и XP

Тело `POST /api/habits/<habit_id>/complete/` может содержать необязательное поле `completed_on` в формате `YYYY-MM-DD`; без него используется текущая дата сервера. Будущую дату передать нельзя. Ответ содержит `created`, `awarded_xp`, `member_id` и текущий `member_xp`, поэтому интерфейс сразу обновляет XP нужного участника. Первая отметка за дату создаёт запись и начисляет награду, а повторный запрос безопасно вернёт `created: false` и `awarded_xp: 0`. Каждая комбинация привычки, пользователя и даты уникальна в БД, поэтому начисление защищено и при повторной отправке запроса.

### История 4: «Сегодня» и часовой пояс

Главная страница отображает только ежедневные привычки и привычки, назначенные на локальный день недели пользователя. Сервер берёт дату из IANA-часового пояса `User.timezone`, а не из часового пояса сервера. Если в старой записи оказался невалидный часовой пояс, для совместимости используется `UTC`; после появления редактирования профиля такое значение следует исправить.

### Приглашения в гильдию

Создатель гильдии открывает «Пригласить» на странице гильдии (`/guilds/<id>/invites`), выбирает срок действия — 1, 7 или 30 дней (по умолчанию 7) — и получает код из 8 символов и ссылку вида `/invite/<код>`. Код и ссылку можно скопировать одной кнопкой. В коде нет похожих символов `0/O` и `1/I/L`, поэтому его удобно продиктовать; регистр при вводе не важен. По ссылке открывается превью гильдии с кнопкой вступления.

- `POST /api/guilds/<guild_id>/invites/` — `{ "expires_in_days": 1 | 7 | 30 }`, создание только владельцем.
- `GET /api/guilds/<guild_id>/invites/` — активные (не истёкшие) приглашения, только владельцу.
- `GET /api/invites/<code>/` — превью для любого вошедшего пользователя: название, описание, цвет, создатель, число участников и `is_member`. Состав участников и привычки не раскрываются.

Участник гильдии получает `403`, пользователь вне гильдии — `404`, как и для остальных ресурсов гильдии. Неизвестный код возвращает `404`, истёкший — `410`.

### Спринт 2, история 2: вступление в гильдию (8 SP)

На главной странице выберите «Вступить по коду» (`/guilds/join`) либо откройте ссылку `/invite/<код>`. После просмотра приглашения нажмите «Вступить в гильдию». Гость сначала входит или регистрируется и возвращается к приглашению. Экран показывает результат вступления и ссылку на гильдию; для действующего участника сразу доступен переход в гильдию.

- `POST /api/invites/<code>/join/` — требует Bearer-токен; тело не требуется.
- Первое вступление: `201`, `{ "guild_id": 42, "created": true }`; повторное: `200`, `created: false`.
- Код нормализуется по регистру и крайним пробелам. Неверный формат — `400`, неизвестный код — `404`, истёкший — `410`, без авторизации — `401`.
- Новому участнику назначаются роль `member` и 0 XP. Повторные запросы, в том числе через другое приглашение той же гильдии, сохраняют роль и XP. Дубликаты защищены уникальным ограничением БД; миграции для истории 2 не требуются.

[Проверка соответствия спринту №2 на 27.10.2026](docs/sprint-2-review.md).

### Спринт 2, история 3: лидерборд участников (10 SP)

Со страницы гильдии откройте «Лидерборд» (`/guilds/<id>/leaderboard`). Таблица показывает место, никнейм, XP и текущий стрик каждого участника, выделяет вас и позволяет переключаться между сортировкой по XP и стрику. Порядок сохраняется в URL (`?sort=xp` или `?sort=streak`).

- `GET /api/guilds/<guild_id>/leaderboard/?sort=xp|streak` — только участникам гильдии; по умолчанию XP. Без входа — `401`, вне гильдии — `404`, неверная сортировка — `400`.
- XP — сохранённый `GuildMember.xp` этой гильдии. Стрик — число последовательных календарных дней с выполнением хотя бы одной привычки гильдии, заканчивающихся сегодня или вчера в часовом поясе участника. Несколько выполнений за день считаются одним днём; будущие даты игнорируются; невалидный часовой пояс заменяется UTC.
- Сортировка: выбранный показатель по убыванию, второй показатель по убыванию, ID пользователя по возрастанию. Места последовательные, включая равенство показателей.
- Ответ: `guild_id`, `guild_name`, `sort`, `members`; участник содержит `member_id`, `user_id`, `username`, `xp`, `streak`, `rank`, `is_current_user`.
- Новые миграции не требуются. Стрик использует существующие даты `completed_on`; запись выполнения пока сохраняет прежнее поведение с датой сервера.

### Проверка изменений

Серверные проверки используют отдельную SQLite-базу в памяти без PostgreSQL и без подключения к рабочей базе:

```bash
cd backend
python manage.py test --settings=config.settings_test
python manage.py makemigrations --check --dry-run --settings=config.settings_test
```

После обновления примените миграции к рабочей базе:

```bash
docker compose exec backend python manage.py migrate
```

PostgreSQL намеренно не публикует порт на хост: к нему обращается только backend-контейнер. Не добавляйте реальный `.env` с паролями в Git; используйте `.env.example` как шаблон.

Проверки frontend:

```bash
cd frontend
pnpm test
pnpm build
```
