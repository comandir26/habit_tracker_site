# inHabit

Геймифицированный трекер привычек с гильдиями.

## Стек
Django + DRF + PostgreSQL, React, Docker Compose.

## Запуск

### Frontend

```bash
cd frontend
pnpm install
pnpm dev
```

Приложение будет доступно по адресу `http://localhost:5173`. В режиме
разработки запросы к `/api` Vite перенаправляет на backend-контейнер.

Для production-сборки frontend:

```bash
docker compose up --build frontend
```

## Спринт 1: текущее состояние

Реализованы подготовка и истории 1–6:

- Создание гильдии с владельцем и просмотр только своих гильдий.
- Создание привычки владельцем: название, ежедневное расписание или выбранные дни недели.
- Сложность и вес награды: лёгкая — 10 XP, средняя — 20 XP, сложная — 30 XP; награда = базовые XP × вес (1–10).
- Форма добавления привычки и список привычек на странице гильдии. Демо доступно по `/guilds/demo`, данные демо сохраняются в текущей сессии браузера.
- Регистрация, вход и выход по JWT. Защищённые страницы перенаправляют гостя на вход; запросы к API выполняются только с `Bearer` access-токеном.

- Участник может отметить привычку выполненной и получает её XP. Повторная отметка той же привычки в тот же день не меняет XP: это обеспечено уникальным ограничением базы данных.
- Список «Сегодня» учитывает часовой пояс пользователя и расписание привычек.

### Регистрация и вход

Откройте `/register`, чтобы создать учётную запись, либо `/login`, чтобы войти. После успешного действия приложение сохраняет access- и refresh-токены в `localStorage`; вручную добавлять токен через DevTools больше не нужно. Access-токен действует 15 минут, refresh-токен — 7 дней. При выходе refresh-токен отзывается сервером, а данные сессии удаляются из браузера.

API аутентификации:

- `POST /api/auth/register/` — `{ "username", "email", "password", "timezone" }`;
- `POST /api/auth/login/` — `{ "username", "password" }`;
- `POST /api/auth/refresh/` — обновление access-токена;
- `GET /api/auth/me/` — текущий пользователь;
- `POST /api/auth/logout/` — `{ "refresh" }`, отзыв refresh-токена.

### API привычек

Все запросы требуют заголовок `Authorization: Bearer <access_token>`.

- `GET /api/habit-difficulties/` — справочник сложности и базовых XP.
- `GET /api/guilds/<guild_id>/habits/` — список для участников гильдии.
- `POST /api/guilds/<guild_id>/habits/` — создание только владельцем.
- `POST /api/habits/<habit_id>/complete/` — отметить выполнение привычки участником гильдии.

- `GET /api/habits/today/` — привычки на текущий день в часовом поясе пользователя (`users.User.timezone`). Ответ содержит локальные `date`, `timezone` и привычки с названием и цветом гильдии.

Пример тела создания:

```json
{
  "name": "Утренняя зарядка",
  "schedule": "weekdays",
  "weekdays": [1, 3, 5],
  "difficulty": "medium",
  "xp_weight": 2
}
```

Дни недели используют ISO-нумерацию: понедельник — 1, воскресенье — 7. Для `daily` список дней нормализуется в `[]`. Поле `xp_reward` рассчитывает сервер (в примере — 40 XP); клиент не задаёт награду напрямую. Название ограничено 120 символами. Ответ гильдии содержит `is_owner` для отображения доступных действий.

### Отметка выполнения и XP

Тело `POST /api/habits/<habit_id>/complete/` может содержать необязательное поле `completed_on` в формате `YYYY-MM-DD`; без него используется текущая дата сервера. Будущую дату передать нельзя. Ответ содержит `created`, `awarded_xp`, `member_id` и текущий `member_xp`, поэтому интерфейс сразу обновляет XP нужного участника. Первая отметка за дату создаёт запись и начисляет награду, а повторный запрос безопасно вернёт `created: false` и `awarded_xp: 0`. Каждая комбинация привычки, пользователя и даты уникальна в БД, поэтому начисление защищено и при повторной отправке запроса.

### История 4: «Сегодня» и часовой пояс

Главная страница отображает только ежедневные привычки и привычки, назначенные на локальный день недели пользователя. Сервер берёт дату из IANA-часового пояса `User.timezone`, а не из часового пояса сервера. Если в старой записи оказался невалидный часовой пояс, для совместимости используется `UTC`; после появления редактирования профиля такое значение следует исправить.

### Приглашения в гильдию

Создатель гильдии открывает «Пригласить» на странице гильдии (`/guilds/<id>/invites`), выбирает срок действия — 1, 7 или 30 дней (по умолчанию 7) — и получает код из 8 символов и ссылку вида `/invite/<код>`. Код и ссылку можно скопировать одной кнопкой. В коде нет похожих символов `0/O` и `1/I/L`, поэтому его удобно продиктовать; регистр при вводе не важен. По ссылке открывается превью гильдии; само вступление по приглашению будет следующей историей.

- `POST /api/guilds/<guild_id>/invites/` — `{ "expires_in_days": 1 | 7 | 30 }`, создание только владельцем.
- `GET /api/guilds/<guild_id>/invites/` — активные (не истёкшие) приглашения, только владельцу.
- `GET /api/invites/<code>/` — превью для любого вошедшего пользователя: название, описание, цвет, создатель, число участников и `is_member`. Состав участников и привычки не раскрываются.

Участник гильдии получает `403`, пользователь вне гильдии — `404`, как и для остальных ресурсов гильдии. Неизвестный код возвращает `404`, истёкший — `410`.

### Проверка изменений

Серверные проверки используют отдельную SQLite-базу в памяти без PostgreSQL и без подключения к рабочей базе:

```bash
cd backend
python manage.py test --settings=config.settings_test
python manage.py makemigrations --check --dry-run --settings=config.settings_test
```

После обновления примените миграции к рабочей базе:

```bash
docker compose exec backend python manage.py migrate
```

PostgreSQL намеренно не публикует порт на хост: к нему обращается только backend-контейнер. Не добавляйте реальный `.env` с паролями в Git; используйте `.env.example` как шаблон.

Проверки frontend:

```bash
cd frontend
pnpm test
pnpm build
```
